## Основные дефекты

P1 ниже означает блокер выпуска; P2 — обязательную доработку перед полной приёмкой. Где есть локальное воспроизведение, это указано. Остальные выводы основаны на статическом анализе указанного пути исполнения.

### A01 · P1 · Невалидная команда становится исполняемой до отклонения

[CommandLeaseWorker.cs:51](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/CommandLeaseWorker.cs:51) сначала вычисляет валидацию, затем безусловно сохраняет команду как `queued`, ожидает ERP ACK и лишь после этого обрабатывает невалидность. Параллельный execution worker уже может её забрать. При ошибке ACK ветка отклонения вообще не выполняется.

Воспроизведено: неверный hash не помешал одному вызову 1С. Требования FR-CMD-002/008 нарушены. Нужно сохранять атомарное решение «допущена к исполнению / отклонена», а не открывать исполнение до обработки валидации. Проверять следует также версии payload по allowlist: [CommandValidator.cs:20](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Application/Commands/CommandValidator.cs:20) сейчас отвергает только неположительные версии.

### A02 · P1 · Истечение срока скрывает уже выполненную команду

[CommandExecutionWorker.cs:44](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/CommandExecutionWorker.cs:44) проверяет expiry раньше ветки `UnknownResult`. Если документ создан, ответ потерян, а срок истёк до восстановления, ERP получит `expired` вместо выяснения фактического результата. Это создаёт риск повторного бизнес-действия новой командой.

Воспроизведено: ни одного status lookup. FR-CMD-007 разрешает истечение до первого выполнения, но не замену выяснения результата после отправки в 1С; требуется сохранить признак первой отправки и сначала разрешать неопределённость.

### A03 · P1 · Принятый ручной ETL-запуск может исчезнуть

Три независимые причины:

- [EtlTrigger.cs:9](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Runtime/EtlTrigger.cs:9): bounded channel с `DropWrite` сообщает успешный `TryWrite`, хотя запрос отброшен при переполнении. Воспроизведено: 17 принятых / 16 доставленных.
- [OnecEtlWorker.cs:28](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/OnecEtlWorker.cs:28): проигравший `ReadAsync` после срабатывания расписания не отменяется; он поглощает следующий ручной запрос. Воспроизведено.
- [CommandExecutionWorker.cs:89](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/CommandExecutionWorker.cs:89): успешный ответ административной команде сохраняется после записи только в RAM, до создания durable ETL job. Перезапуск в этом промежутке теряет работу. Уже прочитанный запрос также отбрасывается при pause/disabled/переполнении spool.

Нужна очередь заданий в SQLite с привязкой к `commandId`; channel должен лишь будить worker. Это прямо следует из §8.4 ТЗ.

### A04 · P1 · Возобновление ETL extraction не реализовано

[RecoverAsync:16](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Persistence/Sqlite/SqliteAgentStore.cs:16) восстанавливает отправку результатов и готовых batch, но не незавершённые ETL runs. [OnecEtlWorker.cs:48](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/OnecEtlWorker.cs:48) каждый раз создаёт новый run; текущая позиция извлечения и фиксированная граница снимка для возобновления не сохраняются.

Воспроизведено: незавершённый run остаётся `running`; `extracting_cursor_json` не ведётся. Повторная загрузка уже зарегистрированных batch частично поддерживается, но это не resume полного импорта по FR-ETL-003/015.

Дополнительное окно сбоя: [FileSpoolStore.cs:41](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Spool/FileSpoolStore.cs:41) переводит файл в `ready` до регистрации в SQLite. При остановке между этими действиями появляется файл без записи batch. На старте перемещаются `.tmp`, но не восстанавливается соответствие ready-файлов и записей БД. Нужен протокол восстановления этого промежуточного состояния.

### A05 · P1 · Retention удаляет данные, необходимые для commit watermark

[SqliteAgentStore.Etl.cs:87](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Persistence/Sqlite/SqliteAgentStore.Etl.cs:87) выбирает старые ACK batch для удаления без проверки завершённости родительского run. При длительной недоступности endpoint завершения run это возможно после успешных ACK отдельных пакетов.

Сначала статус `deleted` мешает run пройти условие завершения, затем cleanup удаляет строки. При этом [GetRunsReadyToCompleteAsync:122](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Persistence/Sqlite/SqliteAgentStore.Etl.cs:122) восстанавливает итоговые watermarks именно из этих строк. Воспроизведено исчезновение watermark после cleanup.

Нужны durable итоговые cursors run и запрет очистки служебных записей до его финального commit. Commit всех watermarks и локального завершения run также сейчас выполняется отдельными операциями, а не одной SQLite-транзакцией; это дополнительная зона аварийных проверок.

### A06 · P1 · Long polling конфликтует с HTTP resilience timeout

[Program.cs:54](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Program.cs:54) добавляет стандартный resilience handler ERP-клиенту без настройки его таймаутов. Локальная проверка установленной библиотеки показала 10 секунд на попытку и 30 секунд на всю операцию, тогда как long poll настроен на 25 секунд.

Следствие конфигурации: корректный сервер, удерживающий пустой запрос 25 секунд, попадает под таймаут попытки раньше штатного ответа. Это не измерение реальной ERP, а установленный конфликт настроек. Нужен отдельный pipeline для lease с согласованными таймаутами и явно заданной политикой повторов.

### A07 · P1 · Переподключение снимает административную паузу

[ErpSessionManager.cs:27](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Runtime/ErpSessionManager.cs:27) при handshake без maintenance безусловно ставит `Normal`, затирая текущие `PauseCommands`, `PauseEtl`, `Drain` или `Disabled`. Если версия удалённой конфигурации не изменилась, ответ 304 не восстановит режим.

Воспроизведено `PauseCommands → Normal`. Требуется единый расчёт эффективного режима с приоритетами источников и восстановлением до запуска рабочих циклов. Кроме того, `PauseEtl` проверяется только перед началом извлечения, а upload worker его не проверяет: семантика паузы и drain нуждается в явном завершении и тестах.

### A08 · P1 · Резерв диска для команд не защищён

`MinimumReservedBytesForCommands` используется в валидации конфигурации и оценке heartbeat, но не как запрет дальнейшей записи ETL. [OnecEtlWorker.cs:34](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/OnecEtlWorker.cs:34) и `FileSpoolStore` ограничивают объём spool, а не фактически свободное место на разделе.

Если диск занят сторонними файлами, ETL может исчерпать резерв, необходимый SQLite и результатам команд. Проверки заполнения реального диска намеренно не выполнялись; вывод подтверждён путями использования настройки. Не закрыты FR-ETL-012 и §23.3; нужны admission/backpressure-проверки перед записью и во время длинного импорта.

### A09 · P2 · Ненадёжные retry, ordering и dead-letter accounting

- [CommandExecutionWorker.cs:59](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Service/Workers/CommandExecutionWorker.cs:59) ограничивает status lookup счётчиком POST-попыток; сам lookup счётчик не увеличивает. Воспроизведено превышение лимита 2 пятью lookup при `AttemptCount=1`. Ветка `NotFound` повторяет POST без аналогичного ограничения. Для unknown result используется фиксированная задержка, а не полная требуемая retry policy.
- [SqliteAgentStore.Commands.cs:56](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Persistence/Sqlite/SqliteAgentStore.Commands.cs:56) проверяет только строго меньшее время получения. При совпадении времени два одинаковых ordering key одновременно допускаются к выполнению; воспроизведено. Проявляется как параллельное выполнение при concurrency > 1; нужна однозначная последовательность и атомарное получение права выполнения.
- [SqliteAgentStore.Etl.cs:171](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/Persistence/Sqlite/SqliteAgentStore.Etl.cs:171) считает `status='dead_letter'`, но локальное завершение записывает `status='result_pending'`, сохраняя dead letter отдельно в `result_status`. Воспроизведён нулевой счётчик при наличии dead-letter результата.

### A10 · P2 · Ошибка OData continuation и неполные режимы синхронизации

[OnecODataClient.cs:32](D:/Project/1C-agent/repo_1c-agent/src/ErpOnecAgent.Infrastructure/OneC/OnecODataClient.cs:32) после последней полной continuation-страницы возвращается к `$skip`, который не учитывает предыдущие continuation-страницы. Воспроизведено повторное чтение `C,D`.

## Архитектурная оценка

Сохранять стоит разделение Domain/Application/Infrastructure/Service, исходящий обмен с ERP, SQLite inbox/outbox, раздельные worker для исполнения и доставки результата, файловый NDJSON/GZip spool, специализированные клиенты 1С command API и OData, mTLS/DPAPI и snapshots конфигурации. Переписывать решение на другой стек оснований нет.

Главная проблема — не состав проектов, а гарантии на границах компонентов: валидация → очередь исполнения; RAM trigger → durable job; файл → запись batch; ACK batch → завершение run → watermark → retention. Именно эти переходы должны стать сохраняемыми, проверяемыми транзакционными протоколами с однозначным recovery.

Нужен единый источник истины для командных состояний и административного режима. Наличие enum/state-machine-класса без использования в рабочем пути не обеспечивает архитектурный инвариант.

| 3. Надёжность команд | Не закрыт | Retry/ordering/expiry/mode/lease/dead letter требуют исправлений и аварийных тестов |
| 4. ETL | Частично | Есть чтение OData, full/incremental primitives, overlap, spool/upload. Durable запуск, extraction resume, retention и сверка не закрыты |
| 5. Security hardening | Частично | mTLS/DPAPI и основы ACL есть; redaction, rotation alerts, подписанная поставка и испытания не закрыты |
| 6. Production operations | Частично | Есть диагностика/backup/скрипты; production MSI, проверенный rollback, dashboard и load/chaos/soak не закрыты |
| 7. Приёмка | Не закрыт | Нет подтверждённого E2E на реальной тестовой ERP+1С, полного аварийного протокола и площадочной приёмки |

Starter-pack отдельно включает реализацию ERP Agent API и расширения 1С. В предоставленном ZIP ERP не обнаружены соответствующие маршруты Agent API; наличие других outbox-модулей не доказывает реализацию этого контракта. Готовое расширение 1С/BSL с журналом идемпотентности в поставленных материалах не найдено. Контракты и mock не заменяют эти части посредника.

Будущие пункты starter-pack — несколько информационных баз, Python analytics, Redis/Celery и другие расширения — не считаются обязательными недоработками v1, если они исключены из её объёма основным ТЗ.

## Рекомендуемая последовательность доведения

1. Закрыть командные гарантии: атомарный допуск после validation, поддерживаемые версии, expiry только до первой отправки, conflict/duplicate-result, lease, надёжный ordering и ограниченный status retry. Добавить регрессионные тесты к найденным сценариям.
2. Сделать ETL job durable; добавить checkpoint/resume, фиксированные границы run, восстановление spool/SQLite и безопасный commit/retention. Проверить kill-процесса на каждой границе и запрет потери принятого задания.
3. Завершить управление режимами/таймаутами/ресурсами, исправить OData paging; реализовать заявленные reconcile/window/error policies. Ограничить размер ответа и подтвердить semantics дат/удалений реальными образцами.
4. Согласовать и реализовать недостающие ERP/1С endpoints. Настройки площадки и бизнес-правила согласовывать с владельцем; отсутствие этих данных не блокирует исправление пунктов 1–3.
5. Подготовить совпадающую с исходниками подписанную поставку, закончить MSI/update/rollback и провести реальную E2E/chaos/load/soak-приёмку.

Критерий готовности — не количество файлов и не только зелёный build: недопустимая команда не исполняется; неопределённый результат не подменяется ошибочным итогом; принятая работа не теряется после restart; watermark не продвигается без подтверждённой выгрузки; очистка и нехватка диска не разрушают эти гарантии; поставляемый EXE проходит проверки на тестовой ERP и 1С.
