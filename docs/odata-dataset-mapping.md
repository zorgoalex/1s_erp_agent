# Избирательный mapping исследованного OData

Источник анализа: локальный `$metadata` OData v3 и выгрузки из `spec_1c-agent/spec_OData/other`. Исходные значения не копируются в репозиторий: набор контрагентов содержит персональные и контактные данные.

## Что использовать

| Приоритет | EntitySet | Назначение | Ключ | Режим |
|---|---|---|---|---|
| 1 | `Catalog_Контрагенты` | минимальная карточка покупателя/поставщика | `Ref_Key` | `manual_only`, пока нет настоящего поля изменения |
| 1 | `Document_ЗаказПокупателя` | заголовок заказа | `Ref_Key` | `manual_only`, поле `Date` является датой документа |
| 1 | `Document_ЗаказПокупателя_Запасы` | товарные строки заказа | `Ref_Key + LineNumber` | вместе с полным reload заказов |
| 1 | `Catalog_Номенклатура` | расшифровка товара | `Ref_Key` | `manual_only` |
| 1 | `Catalog_ЕдиницыИзмерения` | расшифровка единиц | `Ref_Key` | `manual_only` |
| 2 | `AccumulationRegister_ЗаказыПокупателей_RecordType` | плоские движения заказов | `Recorder + LineNumber + Recorder_Type` | условно инкрементальный по `Period`, обязательно со сверкой |

`DataVersion` — непрозрачная версия объекта, а `ДатаСоздания` — дата создания. Ни одно из этих полей нельзя использовать как сортируемый watermark изменения. Без отдельного реквизита изменения или журнала регистрации справочники и документы должны синхронизироваться полным идемпотентным reload.

## Минимальные поля

Контрагенты:

```text
Ref_Key, DataVersion, DeletionMark, Code, Description,
НаименованиеПолное, ВидКонтрагента, Покупатель, Поставщик
```

По умолчанию не выгружать идентификационные номера, телефоны, контактную информацию, банковские и учётные реквизиты, свободный текст `ОсновныеСведения`, дополнительные реквизиты и навигационные ссылки. Они добавляются только по отдельному бизнес-требованию и с явным основанием обработки данных.

Заголовок заказа:

```text
Ref_Key, DataVersion, DeletionMark, Number, Date, Posted,
Контрагент_Key, Организация_Key, СуммаДокумента
```

Строка заказа:

```text
Ref_Key, LineNumber,
Номенклатура, Номенклатура_Type,
ЕдиницаИзмерения, ЕдиницаИзмерения_Type,
Количество, Цена, Сумма, Всего, ДатаОтгрузки
```

В этой конфигурации 1С ссылки `Номенклатура` и `ЕдиницаИзмерения` полиморфные: в метаданных это строки вместе с полями `_Type`, а не поля `_Key`. Расшифровку следует получать отдельными справочниками и соединять в ERP.

## Почему не брать исходный регистр целиком

`AccumulationRegister_ЗаказыПокупателей` возвращает контейнеры регистраторов с вложенным `RecordSet`. В исследованной выгрузке 6 554 контейнера и 27 468 движений; регистраторы относятся не только к заказам, но также к актам и накладным. Для ETL пригоден плоский EntitySet с суффиксом `_RecordType`.

Ключ строки движения строго составной:

```text
Recorder + LineNumber + Recorder_Type
```

`RecordType` (`Receipt`/`Expense`) — направление движения, а не состояние заказа. Остаток заказа должен рассчитываться в ERP как результат движений либо поступать из отдельной согласованной витрины 1С. `Period` является периодом движения и не гарантирует обнаружение задним числом отредактированного старого документа; поэтому инкремент по `Period` допустим только с регулярным `reconcile` или оконным reload.

Пример определения плоского регистра:

```json
{
  "entityCode": "customer_order_movements",
  "odataPath": "AccumulationRegister_ЗаказыПокупателей_RecordType",
  "keyField": "Recorder",
  "keyFields": ["Recorder", "LineNumber", "Recorder_Type"],
  "updatedAtField": "Period",
  "updatedAtEdmType": "Edm.DateTime",
  "deletedField": null,
  "select": [
    "Recorder", "LineNumber", "Recorder_Type", "Period", "Active", "RecordType",
    "Организация_Key", "ЗаказПокупателя_Key", "Номенклатура_Key",
    "Количество", "ДатаОтгрузки"
  ],
  "syncMode": "incremental",
  "pageSize": 500,
  "overlapMinutes": 10,
  "schemaVersion": 1,
  "oDataVersion": 3,
  "enabled": false
}
```

Он оставлен выключенным до согласования семантики остатков и стратегии сверки. Пустой `Etl.Entities` в рабочем `appsettings.json` также сохранён намеренно: реальные выгрузки не должны включаться без контракта ERP и подтверждения состава данных.
