## 2. Agreed baseline (A07a + stage-0 decisions, not re-opened)

- Three independent mode inputs under one lock: persisted local ETL pause, validated remote `AgentMode`, handshake maintenance. `IsReady` only after bootstrap restore. `EffectiveMode` is display-only; worker permissions intersect restrictions (`AgentRuntimeState.cs:12-27`).
- Policy matrix (a07-mode-state.md): local pause blocks extraction only; handshake maintenance blocks lease/execute/extract but not result delivery or batch upload/completion; `Drain` stops admission while accepted commands and results complete; delivery/upload/completion run under every mode once ready.
- CD-LS-2 [PROPOSED] direction already chosen conservatively: on unconfirmed lease ownership, **stop new POSTs; continue status lookup and result delivery**. The same "sent work must stay resolvable" principle is the contract-anchored basis for the split below.
- CD-ETL-2 [PROPOSED]: accepted durable work is deferred, not rejected; rejection is legitimate only before acceptance.
- Contract fact: `sessionId` appears only in `POST /commands/lease` (`erp-agent-api.openapi.yaml:99`). Result PUT, received ACK, batch upload, complete-run, heartbeat, config GET carry no session in the as-built contract.

Handshake/compatibility inputs:

- `ErpSessionManager.GetSessionAsync` (`ErpSessionManager.cs:15-33`): caches `_sessionId` indefinitely; `SetHandshakeMaintenance` is applied **only** on an accepted, version-compatible response. On `!Accepted` (`:24`) or `minimumAgentVersion > current` (`:25-26`) it throws `InvalidOperationException`; on network failure it throws whatever the pipeline throws. In all failure paths the previous `HandshakeMaintenance` flag persists (conservative, fail-closed direction — correct).
- Callers treat rejection identically to transient failure: `CommandLeaseWorker.cs:61-64` invalidates + exponential backoff; `HeartbeatWorker.cs:49` and `ConfigurationWorker.cs:48-56` invalidate + fixed delay. **No latched "incompatible" state exists** — an explicitly rejected agent retries the handshake forever and is indistinguishable from "no handshake yet" (`_sessionId == null` in both cases).
- `HeartbeatWorker.cs:32` calls `sessions.GetSessionAsync` **before** building/sending the heartbeat — so an explicit rejection also suppresses the heartbeat itself (see B6: this conflicts with [TZ §30.2]).
- Session-independent workers (`CommandExecutionWorker`, `ResultDeliveryWorker`, `EtlBatchUploadWorker`, `OnecEtlWorker`) never consult session or compatibility: durable `queued`/`unknown_result` commands keep POSTing to 1C and resolving; results and batches keep flowing toward an ERP that may be rejecting every call (they retry, nothing is dropped).

## 5. Recommended next bounded slice: resolution/admission split in the command path (B2 + B7)

**Local policy implemented by this slice** (root-set; local semantics only — no claim of owner-approved remote protocol):

1. Status lookup of already-sent business commands is permitted whenever `IsReady`, under every command restriction.
2. **ANY** POST to 1C — fresh execution **and** the `NotFound` same-id retry — is denied while `CanExecuteCommands` is false.
3. Administrative callbacks are new work (denied under restriction); the existing sent-admin quarantine path is preserved and never touches 1C.
4. Resolution eligibility must be evaluated in SQL **before** `LIMIT` — a post-fetch pre-filter is rejected: `MaxConcurrency` blocked fresh rows ahead of a due unknown row would starve it, and an all-blocked fetch yields `Task.WhenAll(empty)` tight-polling.

**Design:**

- `AgentModeSnapshot` gains `CanResolveCommandResults => IsReady` (explicit boundary, future-proof).
- Store/query API: a sent-work-only variant of the ready-command query — either a flag on `GetReadyCommandsAsync` or a sibling `GetDueSentCommandsAsync` — adding `AND (c.status='unknown_result' OR c.attempt_count>0 OR c.post_attempt_count>0 OR c.first_sent_at_utc IS NOT NULL)` to the existing predicate. All existing clauses are preserved **verbatim**: `status IN ('queued','retry_waiting','unknown_result')`, `not_before`/`next_attempt` due filters, the same-`ordering_key` `NOT EXISTS` head-of-line guard (a resolution-eligible row still waits behind an active same-key predecessor — ordering is never bypassed), and `ORDER BY priority DESC, received_at_utc, queue_sequence LIMIT`. `post_attempt_count>0`/`first_sent_at_utc` are written by `ClaimPostAttemptCoreAsync` **before** the network call (`SqliteAgentStore.Commands.cs:373`), so a crash-after-claim row still qualifies.
- `CommandExecutionWorker` loop: `if (!IsReady) delay;` → `CanExecuteCommands ? fullQuery() : (CanResolveCommandResults ? sentOnlyQuery() : empty)`. Empty result → existing delay cadence (no spin). `ProcessAsync` invoked only over returned rows.
- `CommandExecutionService.ProcessAsync`: inject `Func<bool> mayStartNewWork` (worker feeds `state.Snapshot.CanExecuteCommands`). Inside the owned pass, after live-row routing:
  - `sentNow` + business → `ResolveStatusThenRetryAsync` unchanged, **except** its `NotFound` branch: `ExecuteFreshAsync` is called only when `mayStartNewWork()`; on denial, close the lookup attempt `unknown_result/NOT_FOUND` and `MarkUnknownResultAsync` with backoff — the row keeps uncertainty and reschedules. When unrestricted, current behavior is unchanged.
  - `sentNow` + administrative → `SaveAdministrativeUnknownResultAsync` unchanged (local write, zero 1C calls, zero callback repeats).
  - `!sentNow` → `mayStartNewWork()` re-checked **inside the pass** before any fresh-work path (`tryAdministrativeAsync`, `ExecuteFreshAsync`, expiry): on denial, release the claim and leave the row untouched — not expired, not dead-lettered, simply ineligible this pass (identical effect to today's loop-level skip). On allow, the existing order is unchanged: expiry on live never-sent evidence → admin callback → `ExecuteFreshAsync`.
- `mayStartNewWork()` is a **linearization of the admission decision, not an atomic mode+network transaction**: a restriction taking effect after the check can still race one in-flight POST; that POST then resolves via the unknown-result machinery. The slice makes no atomicity claim.
- No schema, migration, contract, or other-worker changes.

**Invariants:**

1. Any command with durable send evidence is resolvable when `IsReady` under every source (`PauseCommands`, `Maintenance`, `Disabled`, handshake maintenance, local pause): `GetStatusAsync` may run; **never** a POST.
2. No 1C POST and no administrative side effect while `CanExecuteCommands` is false — including `NotFound` retries and rows fetched just before a mode flip (in-pass recheck).
3. `Drain` unchanged: lease stops, accepted commands (sent or not) still execute and deliver.
4. Lookup uncertainty preserved: resolve-before-retry order, `NotFound` re-POST of the same id (when permitted), attempts closed exactly once by id, separate lookup/POST budgets, unchanged backoff/age limits.
5. Owner fencing preserved: per-pass token before any decision, live-row routing, release of own token only, unclaimed `MarkUnknownResultAsync` fallback unchanged.
6. Mode-source independence: local pause still never gates commands; handshake maintenance still never gates delivery/upload.
7. Ordering: same-`ordering_key` head-of-line guard applies identically in the sent-only query — resolution never bypasses an active predecessor.
8. No starvation/no spin: sent-work filtering happens before `LIMIT`; an all-fresh queue under restriction polls on the normal delay.
9. Admin quarantine safety: sent admin rows resolve only through the local quarantine — `IOnecCommandClient` is never invoked for an administrative type.
10. In-flight calls are never cancelled by a mode change; their outcomes resolve through existing machinery.

**Focused tests:**

- `unknown_result` row + `PauseCommands`/`Maintenance`/`Disabled`/handshake maintenance → 1 `GetStatusAsync`, 0 `ExecuteAsync`.
- `queued` row under each restriction → 0 POSTs, 0 lookups, row still active; under `Drain` → executes.
- `NotFound` under `PauseCommands` → lookup attempt closed `unknown_result/NOT_FOUND`, backoff rescheduled, zero POSTs; after mode lift → next pass looks up again then re-POSTs.
- Starvation: `MaxConcurrency+1` blocked fresh commands on distinct ordering keys ahead of one due `unknown_result` row → the unknown row is still looked up this pass.
- All-fresh queue under `PauseCommands` → bounded polling: elapsed time between store queries stays at the delay cadence (no `Task.WhenAll(empty)` spin).
- Sent-admin row under `PauseCommands` → local dead_letter quarantine; `IOnecCommandClient` call count == 0.
- Mode flip between fetch and claim → fresh POST suppressed, sent row resolved.

## Root disposition before implementation

This is a proposal, not completed behavior. Approved bounded B2/B7 implementation: lookup may continue once ready; POST/admin admission is denied only when CanExecuteCommands is false (local ETL pause alone and Drain still allow POST). Interpret invariants 1-2 at the documented decision point, not as atomic mode/network exclusion. Sent evidence must be consistent in SQL and live routing: UnknownResult, attempt_count, post_attempt_count, first_sent_at_utc; do not select sent-only rows then route them as fresh. Recheck before the actual POST claim path, including after an asynchronous administrative callback returns false. Preserve existing budgets, claim identity, admin quarantine and backoff. All broader B1/B3/B4/B6 compatibility work remains open; this document is not proof of those fixes.
